## 1. 배경과 목적

### 1.1 배경

파일 첨부/업로드 기능은 대부분의 웹 서비스에 존재하지만, 검증 없이 받아들이면 심각한 보안 사고로 이어진다. 대표적인 위협은 다음과 같다.

- **원격 코드 실행(RCE)**: `exe`, `sh`, `jsp`, `php` 등 실행 가능한 파일이 서버에 저장되고, 웹 루트를 통해 접근·실행될 경우 서버 장악으로 이어질 수 있다.
- **악성코드 유포**: 업로드된 파일을 다른 사용자가 다운로드하는 서비스라면, 서버가 악성코드 유포지로 악용된다.
- **경로 조작(Path Traversal)**: `../../etc/passwd` 같은 파일명으로 의도하지 않은 위치에 파일을 쓰게 만들 수 있다.

### 1.2 목적

1. **동작하는 기능**: 확장자 차단 정책을 관리하는 화면과, 그 정책이 **서버에서 실제로 강제되는** 업로드 API를 구현하고 배포한다.
2. **판단의 기록**: 무엇을 고려했고 왜 그렇게 결정했는지(기획/보안/예외/운영), 그리고 그 과정에서 AI를 어떻게 활용했는지를 문서로 남긴다.

> 핵심 관점: 정책 관리 화면(A)만 있고 업로드에서 강제(B)되지 않으면 "정책은 있으나 막지 못하는" 반쪽짜리다. **A + B가 최소 범위**다.

## 3. 정책 설계 — 핵심 판단들

구현 전에 정해야 하는 "정답이 없는" 지점들과, 각각에 대한 판단·근거를 기록한다.

### 3.1 고정 확장자와 커스텀 확장자의 관계

**판단**: 고정 확장자와 커스텀 확장자를 하나의 테이블에 `type` 컬럼으로 구분해 저장하되, **고정 확장자는 커스텀으로 추가할 수 없다.**

- 근거: 고정 확장자를 커스텀에도 추가할 수 있게 하면 "고정에서는 uncheck인데 커스텀에는 존재" 같은 모순 상태가 생긴다. 정책의 단일 진실 공급원(single source of truth)을 유지하기 위해 영역을 상호 배타적으로 만든다.
- 따라서 커스텀 추가 시 고정 확장자 목록과의 중복도 검사한다 (A-8).

### 3.2 확장자 정규화(canonicalization) 규칙

같은 확장자가 표기만 다른 형태로 들어오는 것을 막기 위해, **저장 시점과 검사 시점 모두 동일한 정규화**를 거친다.

| 입력 | 정규화 결과 | 규칙 |
|------|------------|------|
| `SH`, `Sh` | `sh` | 소문자 변환 |
| ` sh ` | `sh` | 앞뒤 공백 제거 |
| `.sh` | `sh` | 선행 `.` 제거 |
| `s h`, `s/h`, `s*h` | 거부 | 영숫자만 허용 (`^[a-z0-9]{1,20}$`) |
| `` (빈 문자열) | 거부 | |

- **근거**: 확장자는 검사의 "키"다. 키가 정규화되어 있지 않으면 `SH`는 통과하고 `sh`는 막히는 우회가 생긴다. 대소문자 무시는 Windows 파일시스템이 대소문자를 구분하지 않는다는 점에서도 필수다.
- 허용 문자를 영숫자로 제한하는 이유: 실제 확장자에 특수문자가 쓰이는 경우는 거의 없고, 허용하면 정규식/비교 로직의 공격 표면만 넓어진다. (`tar.gz` 같은 복합 확장자는 3.4에서 별도 처리)

### 3.3 파일명에서 확장자를 추출하는 규칙 (공격 케이스 포함)

업로드 검증의 핵심. **마지막 `.` 뒤의 문자열**을 확장자로 보되, 다음 케이스를 모두 처리한다.

| # | 파일명 | 추출 확장자 | 처리 |
|---|--------|------------|------|
| 1 | `virus.exe` | `exe` | 정책 검사 |
| 2 | `Virus.EXE` | `exe` (소문자화) | 정책 검사 — 대소문자 우회 차단 |
| 3 | `report.pdf.exe` | `exe` | **마지막 확장자** 기준 — 이중 확장자 위장 차단 |
| 4 | `virus.exe.pdf` | `pdf` | 통과 가능. 마지막 확장자가 실행 불가이므로 위협 아님(주1) |
| 5 | `noext` (확장자 없음) | (없음) | 정책 판단 필요 → **차단** (3.4 참고) |
| 6 | `.gitignore` (dot file) | (없음으로 간주) | 확장자 없음과 동일 취급 → 차단 |
| 7 | `virus.exe.` (trailing dot) | `exe` | 끝의 `.`/공백 제거 후 재추출 — Windows가 저장 시 trailing dot을 제거하는 것을 악용한 우회 차단 |
| 8 | `virus.exe ` (trailing space) | `exe` | 위와 동일 |
| 9 | `virus.exe%00.jpg` / null byte | — | 파일명에 제어문자(0x00–0x1F) 포함 시 **즉시 거부** |
| 10 | `../../evil.jsp` | — | 경로 구분자(`/`, `\`) 포함 시 **즉시 거부** (path traversal) |
| 11 | `ｅｘｅ` (전각 문자) | — | 정규화 후 영숫자 외 문자 → 거부하거나 NFKC 정규화 후 검사(주2) |
| 12 | 255자 초과 파일명 | — | 길이 제한 거부 |

- (주1) `virus.exe.pdf`는 OS가 pdf로 취급하므로 실행 위협은 아니다. 다만 마지막 확장자만 검사한다는 원칙을 CONSIDERATIONS.md에 근거와 함께 명시한다.
- (주2) 유니코드 정규화(NFKC)를 적용해 전각 `ｅｘｅ` → `exe`로 변환 후 검사하는 것을 기본안으로 한다. 변환 후에도 영숫자가 아니면 거부.

### 3.4 경계 상황에 대한 정책 결정

| 상황 | 결정 | 근거 |
|------|------|------|
| 확장자 없는 파일 | **차단** | 확장자가 없으면 정책을 적용할 수 없다. 화이트리스트 사상(fail-safe)에 따라 판단 불가 = 거부. |
| `tar.gz` 같은 복합 확장자 | 마지막 확장자(`gz`)만 검사 | 규칙의 단순성·예측 가능성 우선. `gz` 차단 시 `tar.gz`도 차단되므로 보안상 문제 없음. |
| 커스텀 확장자 삭제 시 이미 업로드된 파일 | 소급 삭제하지 않음 | 정책은 "업로드 시점"에 적용. 소급 적용은 운영 정책(별도 배치)의 영역. |
| 정책 변경과 업로드가 동시에 발생 | 업로드 요청 처리 시점의 DB 정책 기준 | 트랜잭션 범위 내 일관성만 보장하면 충분. |
| 빈 파일(0 byte) | 허용하되 기록 | 확장자 정책과 무관. 필요 시 후속 정책으로. |

### 3.5 왜 블랙리스트인가 (그리고 그 한계)

과제 요구사항은 블랙리스트(차단 목록) 방식이다. 그러나 **보안 관점의 정석은 화이트리스트**(허용 목록)임을 인지하고 문서에 명시한다.

- 블랙리스트의 한계: 새로운 위험 확장자(`ps1`, `vbs`, `msi`, `jar`, `hta`, `jsp`, `php`, ...)가 계속 등장하므로 목록이 완전할 수 없다.
- 그래서 **확장자 차단은 1차 방어선일 뿐**이며, 4장의 심층 방어(defense in depth) 레이어를 함께 설계한다.

## 4. 보안 강화 레이어 (심층 방어)

확장자 검사만으로는 부족하다. 각 레이어는 "앞 레이어가 뚫렸을 때"를 가정한다.

| # | 레이어 | 내용 | 구현 우선순위 |
|---|--------|------|--------------|
| 1 | 확장자 블랙리스트 | 3장의 정책. 서버 측 강제. | 필수 (P0) |
| 2 | 파일명 무해화 | 저장 시 원본 파일명을 쓰지 않고 **서버가 생성한 UUID로 저장**. 원본 파일명은 DB 메타데이터로만 보관. | 필수 (P0) — path traversal, 파일명 인젝션을 원천 차단 |
| 3 | 저장 위치 격리 | 웹 루트 밖 디렉토리에 저장. 정적 서빙 경로와 분리. | 필수 (P0) — 업로드 파일이 URL로 직접 실행되는 것을 차단 |
| 4 | 파일 크기 제한 | 요청/파일 단위 최대 크기 (예: 10MB). | 필수 (P0) — DoS 방지 |
| 5 | MIME 스니핑 검증 | 매직 넘버(파일 시그니처)로 실제 타입 확인. 예: 확장자는 `jpg`인데 시그니처가 `MZ`(PE 실행 파일)이면 거부. | 권장 (P1) — Apache Tika 또는 시그니처 직접 검사 |
| 6 | Content-Disposition | 다운로드 제공 시 `attachment` + 안전한 파일명으로 응답, `X-Content-Type-Options: nosniff`. | 권장 (P1) — 브라우저에서의 실행/스니핑 방지 |
| 7 | 실행 권한 제거 | 저장 파일에 실행 비트 부여 안 함 (Linux 배포 시). | 권장 (P1) |
| 8 | 레이트 리밋 / 인증 | 데모 범위에서는 생략하되 CONSIDERATIONS에 한계로 명시. | 범위 외 (P2) |
| 9 | 바이러스 스캔 (ClamAV 등) | 실서비스라면 필요. 데모에서는 문서로만. | 범위 외 (P2) |

> P0는 반드시 구현, P1은 시간 내 구현 목표, P2는 문서에 한계·향후 과제로 명시.

## 5. 시스템 설계

### 5.1 기술 스택 (안)

| 구분 | 선택 | 근거 |
|------|------|------|
| 백엔드 | Spring Boot 3.x (Java 17+) | 주력 스택. Bean Validation, 예외 처리, 테스트 생태계 활용 |
| DB | 배포: MySQL(또는 PostgreSQL) / 테스트: H2 | 정책 영속성 요구. 테스트는 인메모리로 빠르게 |
| ORM | Spring Data JPA | 단순 CRUD 중심이라 충분 |
| 프론트 | Thymeleaf + vanilla JS (fetch) | SPA가 필요 없는 규모. 배포 단순화(단일 jar) |
| 파일 저장 | 로컬 디스크 (웹 루트 밖) | 데모 범위. 실서비스라면 S3 등 오브젝트 스토리지 — 문서에 명시 |

### 5.2 DB 스키마

```sql
-- 확장자 정책 (고정 + 커스텀 통합)
CREATE TABLE blocked_extension (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    name        VARCHAR(20)  NOT NULL,            -- 정규화된 확장자 (소문자, dot 없음)
    type        VARCHAR(10)  NOT NULL,            -- FIXED | CUSTOM
    is_blocked  BOOLEAN      NOT NULL DEFAULT TRUE, -- FIXED의 check 상태 (CUSTOM은 항상 TRUE)
    created_at  DATETIME     NOT NULL,
    updated_at  DATETIME     NOT NULL,
    CONSTRAINT uq_extension_name UNIQUE (name)     -- 중복 방지를 DB 레벨에서도 보장
);

-- 업로드 파일 메타데이터
CREATE TABLE uploaded_file (
    id             BIGINT PRIMARY KEY AUTO_INCREMENT,
    original_name  VARCHAR(255) NOT NULL,  -- 표시용 (응답 시 이스케이프)
    stored_name    VARCHAR(100) NOT NULL,  -- UUID + 검증된 확장자
    extension      VARCHAR(20),
    size_bytes     BIGINT       NOT NULL,
    content_type   VARCHAR(100),
    created_at     DATETIME     NOT NULL
);
```

설계 포인트:
- **UNIQUE 제약을 DB에 건다**: 애플리케이션의 중복 검사(A-7)는 동시 요청에서 race condition이 가능하다. 최종 방어선은 DB 제약이고, 제약 위반 예외를 "중복" 응답으로 변환한다.
- 고정 확장자 7종은 애플리케이션 시작 시(또는 마이그레이션 스크립트로) `type=FIXED, is_blocked=false`로 시드한다. → "default unCheck" 충족.
- 커스텀 200개 제한은 `type=CUSTOM`의 count로 서버에서 검사.

### 5.3 API 설계

| Method | Path | 설명 | 주요 응답 |
|--------|------|------|----------|
| `GET` | `/api/extensions` | 고정(체크 상태 포함) + 커스텀 목록 + 커스텀 개수 | 200 |
| `PATCH` | `/api/extensions/fixed/{name}` | 고정 확장자 check/uncheck (body: `{blocked: true}`) | 200 / 404 |
| `POST` | `/api/extensions/custom` | 커스텀 추가 (body: `{name: "sh"}`) | 201 / 400(형식) / 409(중복·고정과 충돌) / 422(200개 초과) |
| `DELETE` | `/api/extensions/custom/{name}` | 커스텀 삭제 | 204 / 404 |
| `POST` | `/api/files` | 파일 업로드 (multipart) | 201 / 400(파일명 위험) / 422(차단 확장자) / 413(크기 초과) |

**차단 응답 예시** (B-2 "명확한 사유"):

```json
  "message": "차단된 확장자입니다: 'exe' (고정 차단 정책)",
  "extension": "exe",
  "policyType": "FIXED"
}
```

### 5.4 업로드 검증 파이프라인 (서버)

```
multipart 수신
  → ① 파일명 안전성 검사 (null byte / 경로 구분자 / 제어문자 / 길이) — 실패 시 400
  → ② 파일명 정규화 (trailing dot·공백 제거, NFKC)
  → ③ 확장자 추출 (마지막 '.') — 없으면 422 (확장자 없는 파일 차단 정책)
  → ④ 확장자 정규화 (소문자)
  → ⑤ 정책 조회: FIXED(is_blocked=true) ∪ CUSTOM 에 포함되면 422 + 사유
  → ⑥ (P1) 매직 넘버 검사: 실행 파일 시그니처(MZ, ELF, #!) 감지 시 422
  → ⑦ UUID 파일명 생성 → 웹 루트 밖 저장 → 메타데이터 DB 기록 → 201
```

### 5.5 화면 구성 (와이어프레임)

```
┌─────────────────────────────────────────────┐
│  파일 업로드 확장자 차단 관리                    │
├─────────────────────────────────────────────┤
│  고정 확장자                                  │
│  ☐ bat  ☐ cmd  ☐ com  ☐ cpl  ☐ exe  ☐ scr  ☐ js │
├─────────────────────────────────────────────┤
│  커스텀 확장자                     (3 / 200)  │
│  [ 확장자 입력 (최대 20자)     ]  [ 추가 ]     │
│  ┌─────────────────────────────────────┐    │
│  │  sh ✕   php ✕   jsp ✕               │    │
│  └─────────────────────────────────────┘    │
├─────────────────────────────────────────────┤
│  파일 업로드 테스트                            │
│  [ 파일 선택 ]  [ 업로드 ]                     │
│  결과: ✅ 업로드 성공 / ❌ 차단됨: exe (고정 정책) │
│  업로드된 파일 목록                            │
└─────────────────────────────────────────────┘
```

- 클라이언트 검증(입력 길이, 즉시 중복 표시)은 UX용으로만 두고, **모든 검증은 서버에서 반복**한다.
- 체크박스 토글은 즉시 PATCH 호출(낙관적 UI + 실패 시 롤백 또는 단순 재조회).

## 6. 테스트 계획

### 6.1 정책 관리 (단위 + 통합)

- 고정 확장자 토글 → DB 반영 → 재조회 시 유지
- 커스텀 추가: 정상 / 21자 / 빈 값 / 특수문자 / `.sh` 입력 / 대문자 입력
- 중복: 같은 값, 대소문자만 다른 값, 고정 확장자와 같은 값
- 200개 경계: 200번째 성공, 201번째 실패
- 동시 추가 race: 동일 확장자 동시 요청 → 하나만 성공 (DB UNIQUE 검증)

### 6.2 업로드 — 파일명 공격 파라미터화 테스트 (핵심)

`@ParameterizedTest`로 3.3의 표를 그대로 테스트 케이스화한다.

```java
@ParameterizedTest
@CsvSource({
    "virus.exe,          422, BLOCKED_EXTENSION",
    "Virus.EXE,          422, BLOCKED_EXTENSION",
    "report.pdf.exe,     422, BLOCKED_EXTENSION",
    "virus.exe.,         422, BLOCKED_EXTENSION",   // trailing dot
    "'virus.exe ',       422, BLOCKED_EXTENSION",   // trailing space
    "noext,              422, NO_EXTENSION",
    ".gitignore,         422, NO_EXTENSION",
    "../../evil.jsp,     400, INVALID_FILENAME",
    "safe.png,           201, -",
    "virus.exe.pdf,      201, -"                     // 마지막 확장자 기준
})
```

- null byte(`\0`) 케이스는 CsvSource로 표현이 어려우므로 별도 `@MethodSource`로.
- 매직 넘버 검사(P1) 구현 시: 내용은 `MZ`로 시작하지만 이름은 `photo.jpg`인 파일 → 422.

### 6.3 E2E (수동 + 배포 후)

- 배포 URL에서: exe 체크 → exe 업로드 시도 → 차단 메시지 확인 → 체크 해제 → 업로드 성공 확인
- 새로고침 후 정책 유지 확인

## 7. 배포 계획

| 후보 | 장점 | 단점 |
|------|------|------|
| **AWS EC2 + RDS(or 로컬 MySQL)** | 자유도 높음, 파일 저장 단순 | 초기 셋업 비용 |
| Railway / Fly.io / Koyeb | 배포 간단, 무료 티어 | 파일시스템 휘발성 → 업로드 파일 유지에 볼륨 필요 |
| Cloudflare Workers + R2 + D1 | 서버리스 | Spring 불가, 스택 변경 필요 |

**기본안**: Spring Boot 단일 jar + MySQL을 클라우드 VM(EC2 등)에 배포. 무료 PaaS 사용 시 "재배포 시 업로드 파일 소실" 한계를 CONSIDERATIONS에 명시하고, 정책 데이터(DB)는 영속 스토리지에 둔다.

## 8. AI 활용 계획 (PROMPT_LOG.md 운영 방침)

이 과제는 "AI를 어떻게 사용했는가"도 평가 대상이므로, 구현 중 실시간으로 기록한다.

기록 형식 (건별):

```markdown
## [번호] 주제 (예: 파일명 정규화 규칙 설계)
- 시점 / 단계: 설계 | 구현 | 테스트 | 디버깅
- 프롬프트 요지: (실제 프롬프트 또는 요약)
- AI 답변 요지:
- 채택 여부와 판단: 그대로 채택 / 수정 채택 / 기각 — **이유**
- 검증 방법: 테스트로 확인 / 공식 문서 대조 / 직접 재현
```

방침:
- AI 제안을 **그대로 쓰지 않은 사례**(기각·수정)를 최소 2건 이상 남긴다 — 검증 능력을 보여주는 핵심.
- 보안 관련 코드는 AI 출력이더라도 반드시 테스트 케이스로 검증 후 채택.
- 활용 영역 구분: (1) 정책 설계 브레인스토밍 (공격 케이스 발굴), (2) 보일러플레이트 생성, (3) 테스트 케이스 확장, (4) 문서 초안.
