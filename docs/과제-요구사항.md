# 과제 요구사항 (원문)

> 과제로 받은 원문을 그대로 보관한다. 3장의 고려사항 목록은 [PROMPT_LOG.md](../PROMPT_LOG.md)에서
> "과제 목록 밖에서 발굴한 고려사항"을 가르는 기준이다.

## 1. 배경 & 목적

어떤 파일들은 첨부/업로드 시 보안에 문제가 될 수 있습니다. 특히 exe, sh 등의 실행 파일이 서버에 올라가 실행될 경우 위험이 있어, 파일 확장자 차단을 포함한 안전한 파일 업로드 처리가 필요합니다.

이번 과제의 목적은 두 가지입니다.

1. 파일 업로드 기능을 실제로 동작하는 형태로 구현하고 배포한다.
2. 구현보다 더 중요한 것 — 어떤 점들을 고려했는지(기획/보안/예외/운영), 그리고 그 판단·구현 과정에서 AI를 어떻게 사용했는지를 문서로 남긴다.

정답이 정해진 과제가 아닙니다. "무엇을 고려했고, 왜 그렇게 판단했는가"의 깊이와 근거를 봅니다.

## 2. 과제 개요

파일 업로드 시 확장자 기반 차단 정책을 관리하고, 실제 파일 업로드 시 그 정책이 적용되는 기능을 만드세요.

### 최소 구현 범위 (필수)

**A. 확장자 차단 정책 관리 화면**

- 고정 확장자: 차단을 자주 하는 확장자 리스트 (bat, cmd, com, cpl, exe, scr, js)
  - default는 unCheck 상태
  - check/uncheck 시 DB에 저장 → 새로고침 시 유지
  - (고정 확장자는 아래 커스텀 확장자 영역에 표시되지 않음)
- 커스텀 확장자
  - 입력 최대 길이 20자
  - "추가" 클릭 시 DB 저장 후 목록 영역에 표시
  - 최대 200개까지 추가 가능
  - 각 항목 옆 X 클릭 시 DB에서 삭제
  - 중복 추가 방지 (예: sh 추가 후 다시 sh 추가 시 처리)

**B. 실제 파일 업로드 처리**

- 위에서 설정한 차단 정책이 실제 업로드에 적용되어야 함
- 차단 대상 파일 업로드 시 명확한 사유와 함께 거부
- 정상 파일은 업로드 성공 처리 (저장 위치/방식은 자유)

A만 있고 B가 없으면 "정책은 있으나 실제로 막지 못하는" 화면일 뿐입니다. 정책이 실제 업로드에서 강제되는 것까지가 최소 범위입니다.

## 3. 기획/개발 고려사항 (핵심 평가 영역)

아래는 "이런 것도 고려했나요?" 를 묻는 항목입니다. 전부 구현할 필요는 없습니다. 하지만 구현했든, 의도적으로 제외했든, 각 항목에 대한 판단과 근거를 문서에 남기세요. ("고려 안 함"도 근거가 있으면 됩니다.)

### 3-1. 검증/보안 관점

- 확장자만 믿어도 되는가? (실제 파일 내용/시그니처(매직 넘버)와의 불일치 — 예: report.jpg 인데 실제로는 실행 파일)
- 대소문자 / 이중 확장자 (file.exe.txt, file.PDF, .tar.gz)
- 확장자 없는 파일, 점(.)으로 시작하는 파일(.env), 매우 긴 파일명
- 확장자 입력값 검증 (특수문자·공백·유니코드·. 포함 여부 정규화)
- 서버 사이드 검증의 필요성 (클라이언트 검증만으로는 우회 가능)
- 업로드 파일 크기 제한 / 파일 개수 제한
- 저장 시 원본 파일명 사용 위험 (경로 조작, 실행 가능 위치 저장) 및 대응
- MIME 타입 스푸핑

### 3-2. 정책/데이터 관점

- 고정 확장자와 커스텀 확장자가 겹칠 때 (예: 커스텀에 exe 입력)
- 정책 변경 이력/감사(누가 언제 무엇을 바꿨는지)의 필요 여부
- 200개 / 20자 등 제한의 근거와 초과 시 UX
- 대량(수백 개) 확장자 조회/저장 시 성능·인덱스 고려

### 3-3. UX/예외 관점

- 차단 시 사용자에게 보여줄 메시지(무엇이, 왜 막혔는지)
- 로딩/에러/네트워크 실패 상태 처리
- 저장 실패 시 화면 상태와 DB 상태의 일관성
- 접근성/반응형(선택)

### 3-4. 운영 관점

- 새로고침/동시 편집 시 정합성
- 로그/모니터링 관점에서 무엇을 남길 것인가
- 향후 확장(예: 사용자별 정책, 화이트리스트 방식 전환) 고려 여부
