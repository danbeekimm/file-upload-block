# 배포 가이드 (GitHub Actions → SSH 클라우드 VM)

`main` 에 push 하면 GitHub Actions 가 **테스트 → Docker 이미지 빌드(GHCR 푸시) → SSH 배포** 를 수행합니다.
VM 에는 이미 운영 중인 **nginx** 와 **PostgreSQL(5432)** 이 있고, 앱은 그 둘에 붙는 컨테이너 하나만 추가합니다.

```
인터넷 ──HTTPS──▶ Cloudflare (프록시, 공개 TLS)
                     │ HTTPS (Origin 인증서)
                     ▼
                  nginx (기존, 443, file-upload-block.danbee.site, real_ip = CF-Connecting-IP)
                     │ proxy_pass
                     ▼
            127.0.0.1:8090  app 컨테이너 (network_mode: host, 루프백에만 바인드)
                     │ JDBC
                     ▼
            127.0.0.1:5432  PostgreSQL 17 (기존 `antcamp-postgres` 컨테이너, 전용 DB `fileupload`)
                     │
                     ▼ 업로드 파일
                   S3
```

| 파일 | 역할 |
|---|---|
| [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml) | 워크플로 (test / build-push / deploy 3개 잡) |
| [`deploy/docker-compose.yml`](../deploy/docker-compose.yml) | 서버에서 실행되는 compose (앱 컨테이너 1개) |
| [`deploy/deploy.sh`](../deploy/deploy.sh) | 서버에서 실행되는 배포 스크립트 (pull → 스키마 1회 적용 → up --wait → 스모크) |
| [`deploy/nginx/file-upload-block.danbee.site.conf`](../deploy/nginx/file-upload-block.danbee.site.conf) | nginx 서버 블록 (수동 1회 설치) |
| [`deploy/nginx/cloudflare-real-ip.conf`](../deploy/nginx/cloudflare-real-ip.conf) | Cloudflare 대역 → 실제 클라이언트 IP 복원 스니펫. [`refresh-cloudflare-ips.sh`](../deploy/nginx/refresh-cloudflare-ips.sh) 로 갱신 |
| [`deploy/db/init-prod-db.sql`](../deploy/db/init-prod-db.sql) | 기존 PostgreSQL 에 전용 롤/DB 생성 (수동 1회 실행) |
| [`docker-compose.prod.yml`](../docker-compose.prod.yml) | (대안) DB 컨테이너까지 포함한 단일 호스트 독립 구성. CI 배포에서는 사용하지 않음 |

## 1. 설계 선택

| 항목 | 선택 | 이유 |
|---|---|---|
| 이미지 빌드 위치 | GitHub Actions 의 ARM 러너(`ubuntu-24.04-arm`)에서 `linux/arm64` 로 빌드해 GHCR(`ghcr.io/danbeekimm/file-upload-block`)에 푸시 | VM 이 OCI Ampere A1(aarch64). VM 에 JDK/Gradle 이나 빌드 메모리가 필요 없고, 같은 이미지를 태그(`sha-xxxxxxx`)로 롤백할 수 있음 |
| 컨테이너 네트워크 | `network_mode: host` | VM 의 기존 PostgreSQL 에 `127.0.0.1:5432` 로 바로 접속. `listen_addresses`/`pg_hba` 를 손대지 않아도 되고, PostgreSQL 이 네이티브든 컨테이너든 동일 |
| 앱 바인드 | `SERVER_ADDRESS=127.0.0.1`, 포트 `APP_PORT`(기본 8090) | host 네트워크여도 루프백에만 열려 nginx 를 거치지 않고는 접근 불가 |
| 클라이언트 IP | nginx `real_ip`(Cloudflare 대역만 `CF-Connecting-IP` 신뢰) → `X-Forwarded-For $remote_addr` → 앱 `FORWARD_HEADERS_STRATEGY=native` | Cloudflare 와 nginx 두 홉을 거쳐도 IP 제한/차단이 실제 클라이언트 IP 로 동작. Cloudflare 대역 밖에서 온 요청의 헤더는 무시되고, Tomcat 은 루프백(nginx)만 신뢰하므로 위조 경로가 없음 (CONSIDERATIONS.md) |
| DB | 기존 PostgreSQL(ants-camp 의 `antcamp-postgres` 컨테이너, pg17)에 전용 롤 `fileupload` + DB `fileupload` (public 스키마) | `antcamp` DB 와 격리. 앱은 `search_path` 를 바꾸지 않으므로 전용 DB 가 전용 스키마보다 단순 |
| 스키마 적용 | 첫 배포 시 `deploy.sh` 가 `upload_policy` 테이블이 없을 때만 `schema.sql` 적용 | 수동 단계 최소화. 이후 배포에서는 건너뜀 (DDL 변경은 별도 마이그레이션 필요 — 5장) |
| 비밀값 | GitHub Secrets → 배포 시 서버 `.env` 생성 | 서버에 수동으로 `.env` 를 만들 필요 없음. 값 변경은 Secrets 수정 후 `Run workflow` |

## 2. 최초 1회 준비 (VM)

### 2-1. Docker

```bash
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER && newgrp docker
docker compose version      # v2.x 필요 (--wait 옵션 사용)
```

### 2-2. 앱 포트 결정

```bash
ss -ltnp | grep -E ':(8090)\b' || echo "8090 사용 가능"
```

8090 이 이미 쓰이면 비어 있는 포트를 골라 GitHub 변수 `APP_PORT` 와 nginx 설정의 `proxy_pass` 포트를 같게 맞춥니다.

### 2-3. PostgreSQL 전용 롤/DB

VM 의 PostgreSQL 은 ants-camp 의 `docker-compose.lite.yml` 이 띄운 **`antcamp-postgres` 컨테이너**(`pgvector/pgvector:pg17`, `127.0.0.1:5432`)입니다.
슈퍼유저는 그 compose 의 `POSTGRES_USER` (ants-camp `.env`, 값 `antcamp`) 이고, 비밀번호는 같은 파일의 `POSTGRES_PASSWORD` 입니다.
`docker exec` 로 컨테이너 안의 psql 을 쓰면 비밀번호 입력 없이(로컬 소켓, trust) 접속됩니다.

파일을 VM 에 옮길 필요 없이 로컬에서 ssh 로 파이프하면 됩니다 (롤/DB 가 이미 있으면 건너뜁니다. `db_password` 는 GitHub Secret `DB_PASSWORD` 와 같은 값으로).

```bash
# 로컬 PC 에서 (cloud 프로필). 저장소 루트에서 실행
ssh cloud "docker exec -i antcamp-postgres psql -U antcamp -d postgres \
  -v db_user=fileupload -v db_name=fileupload -v db_password='<비밀번호>'" < deploy/db/init-prod-db.sql

# 확인 — 앱과 같은 경로(호스트 네트워크 → 127.0.0.1:5432)로 새 롤로 접속
ssh cloud "docker run --rm --network host -e PGPASSWORD='<비밀번호>' postgres:17-alpine \
  psql -h 127.0.0.1 -U fileupload -d fileupload -c 'select current_user, current_database()'"
```

> 슈퍼유저 이름을 모르겠으면 `docker exec antcamp-postgres printenv POSTGRES_USER` 또는
> `grep POSTGRES_USER ~/ants-camp/.env`. 공식 postgres 이미지의 `pg_hba.conf` 는 `host all all all scram-sha-256` 이라
> 호스트 127.0.0.1 에서의 비밀번호 접속이 기본으로 허용됩니다.

테이블은 만들지 않습니다. 첫 배포 때 `deploy.sh` 가 `schema.sql` 을 적용합니다.

### 2-4. Cloudflare + nginx

`danbee.site` 는 Cloudflare 가 프록시합니다. 이미 `portfolio.danbee.site` 가 **`*.danbee.site` Origin 인증서**(`/etc/nginx/ssl/portfolio-origin.pem`)로
오리진 443 을 종단하고 있으므로 같은 인증서를 재사용합니다. DNS 도 와일드카드로 해석되어 추가 레코드가 필요 없었습니다 (2026-10-01 확인).
새 서브도메인이 해석되지 않으면 Cloudflare DNS 에 `file-upload-block` A 레코드(VM IP, Proxied)를 추가합니다.

nginx 설정 설치 (로컬 PC 에서, 포트를 바꿨다면 `proxy_pass` 수정):

```bash
scp deploy/nginx/cloudflare-real-ip.conf deploy/nginx/file-upload-block.danbee.site.conf deploy/nginx/refresh-cloudflare-ips.sh cloud:/tmp/
ssh cloud 'sudo mkdir -p /etc/nginx/snippets \
  && sudo cp /tmp/cloudflare-real-ip.conf /etc/nginx/snippets/ \
  && sudo cp /tmp/file-upload-block.danbee.site.conf /etc/nginx/sites-available/ \
  && sudo install -m 755 /tmp/refresh-cloudflare-ips.sh /usr/local/sbin/ \
  && sudo ln -sf /etc/nginx/sites-available/file-upload-block.danbee.site.conf /etc/nginx/sites-enabled/ \
  && sudo nginx -t && sudo systemctl reload nginx'
```

설정의 핵심 두 가지:

- `client_max_body_size 100m` — nginx 기본값(1m)이면 앱이 파일별 판정을 하기 전에 nginx 가 413 으로 끊습니다. Cloudflare Free 플랜의 본문 상한도 100MB 입니다.
- `snippets/cloudflare-real-ip.conf` — Cloudflare 대역에서 온 요청만 `CF-Connecting-IP` 를 `$remote_addr` 로 씁니다. 이게 없으면 앱의 IP 제한/차단이 Cloudflare 엣지 IP 단위로 걸려 전체 사용자가 함께 차단됩니다.
  대역은 가끔 바뀌므로 `sudo refresh-cloudflare-ips.sh` 를 분기에 한 번 정도 실행합니다.

앱이 아직 떠 있지 않아도 nginx 설치는 가능합니다 (502 가 날 뿐).

### 2-5. SSH 배포 키

두 가지 중 하나를 고릅니다.

**A. 기존 키 재사용 (ants-camp 와 동일)** — 가장 빠름. ants-camp 의 `OCI_SSH_KEY` 와 같은 키입니다 (`ssh -G cloud | grep identityfile`).

```bash
cat /Users/narris/keys/ssh-key-2025-12-27.key     # 전체 내용 → Secret SSH_PRIVATE_KEY
# SSH_HOST = ssh -G cloud | grep hostname 의 값,  SSH_USER = ubuntu
```

**B. 이 저장소 전용 키 (권장)** — 유출 시 이 키만 폐기하면 됩니다.

```bash
# 로컬 PC 에서
ssh-keygen -t ed25519 -C "github-actions file-upload-block" -f ~/.ssh/fub-deploy -N ""
# 공개키를 VM 의 ubuntu 계정에 등록 (cloud 프로필로 접속)
ssh cloud 'mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys' < ~/.ssh/fub-deploy.pub
ssh -i ~/.ssh/fub-deploy ubuntu@<VM IP> 'echo ok'        # 새 키로 접속 확인
cat ~/.ssh/fub-deploy                                     # 전체 내용(-----BEGIN ... END-----) → Secret SSH_PRIVATE_KEY
```

둘 다 개인키는 OpenSSH 형식 그대로 줄바꿈 포함해 붙여넣습니다. 배포 사용자(`ubuntu`)는 이미 `docker` 그룹에 있습니다.

## 3. GitHub 설정 (Settings → Secrets and variables → Actions)

워크플로는 `production` environment 를 사용합니다. Secrets/Variables 는 Repository 수준 또는 `production` environment 수준 어느 쪽에 넣어도 됩니다.

**Secrets**

| 이름 | 필수 | 설명 |
|---|---|---|
| `SSH_HOST` | ✅ | VM 공인 IP (ants-camp `OCI_HOST` 와 동일) |
| `SSH_USER` | ✅ | `ubuntu` (docker 그룹) |
| `SSH_PRIVATE_KEY` | ✅ | 2-5 의 개인키 (OpenSSH 형식 전체) |
| `DB_PASSWORD` | ✅ | 2-3 에서 만든 롤 비밀번호 |
| `AWS_ACCESS_KEY_ID` | S3 모드 | `s3-uploader` 키 (README 의 IAM 정책) |
| `AWS_SECRET_ACCESS_KEY` | S3 모드 | 〃 |

**Variables** (없으면 괄호의 기본값)

| 이름 | 기본값 | 설명 |
|---|---|---|
| `APP_PORT` | `8090` | 앱이 127.0.0.1 에 여는 포트. nginx `proxy_pass` 와 동일하게 |
| `APP_DIR` | `~/file-upload-block` | 서버의 배포 디렉터리 (compose, .env, schema.sql, deploy.sh) |
| `SSH_PORT` | `22` | |
| `DB_PORT` / `DB_NAME` / `DB_USER` | `5432` / `fileupload` / `fileupload` | 2-3 과 동일하게 |
| `STORAGE_MODE` | `s3` | `local` 이면 컨테이너 내부 저장(휘발) |
| `S3_BUCKET` / `S3_REGION` / `S3_PREFIX` | `work-841820566166-us-east-1-an` / `us-east-1` / `uploads/` | |

GHCR 이미지는 GitHub 자동 토큰(`GITHUB_TOKEN`)으로 푸시·풀 하므로 별도 레지스트리 자격 증명은 필요 없습니다.
배포 시 서버에서 `docker login ghcr.io` 를 그 토큰으로 수행하므로 패키지가 private 이어도 동작합니다.

## 4. 워크플로 동작

| 잡 | 트리거 | 내용 |
|---|---|---|
| `test` | PR, main push, 수동(태그 미지정) | PostgreSQL 16 서비스 컨테이너(55432) 위에서 `./gradlew test` (단위 + 통합). 실패 시 리포트 아티팩트 업로드 |
| `build-push` | main push, 수동(태그 미지정) | ARM 러너에서 멀티스테이지 `Dockerfile` 을 `linux/arm64` 로 빌드 → `ghcr.io/danbeekimm/file-upload-block:sha-xxxxxxx` 와 `:latest` 푸시. GHA 캐시로 의존성 레이어 재사용 |
| `deploy` | build-push 성공 후, 또는 수동(태그 지정) | ① `deploy/docker-compose.yml`, `deploy.sh`, `schema.sql` 복사 ② Secrets 로 `.env` 생성 ③ `deploy.sh` 실행 ④ 도메인으로 HTTP 200 확인(경고만) |

`deploy.sh` 는 서버에서 다음을 순서대로 합니다.

1. GHCR 로그인 → `docker compose pull`
2. `SELECT to_regclass('public.upload_policy')` 로 스키마 유무 확인 → 없으면 `schema.sql` 적용 (postgres 이미지의 `psql` 사용, 호스트에 psql 불필요)
3. `docker compose up -d --wait` — healthcheck(`GET /api/admin/policies`, DB 왕복 포함) 통과까지 대기. 실패 시 로그 100줄 출력 후 중단
4. `curl 127.0.0.1:APP_PORT/api/admin/policies` 스모크 → 미사용 이미지 정리

컨테이너 재생성 사이에 수 초의 다운타임이 있습니다 (단일 인스턴스).

### 배포 확인

```bash
# 서버에서
docker compose -f ~/file-upload-block/docker-compose.yml ps        # healthy
docker logs -f file-upload-block
curl -s http://127.0.0.1:8090/api/admin/policies | head -c 200

# 외부에서
curl -s https://file-upload-block.danbee.site/api/admin/policies                     # 200 + 고정 7개
curl -X POST https://file-upload-block.danbee.site/api/uploads -F files=@some.txt   # STORED
# 화면에서 exe 체크 후
curl -X POST https://file-upload-block.danbee.site/api/uploads -F files=@evil.exe   # BLOCKED_EXTENSION
```

IP 차단이 실제 클라이언트 IP 로 기록되는지는 서버 로그의 IP 가 nginx(127.0.0.1)가 아닌 접속 IP 인지로 확인합니다.

### 롤백

Actions → `CI / Deploy` → `Run workflow` → `image_tag` 에 이전 태그(`sha-xxxxxxx`, GHCR 패키지 페이지 또는 이전 실행 로그에서 확인) 입력.
테스트/빌드를 건너뛰고 그 이미지로 `deploy` 만 실행합니다. 서버에서 직접 하려면:

```bash
cd ~/file-upload-block && APP_IMAGE=ghcr.io/danbeekimm/file-upload-block:sha-xxxxxxx docker compose up -d --wait
```

## 5. 운영 메모

| 항목 | 내용 |
|---|---|
| 스키마 변경 | `deploy.sh` 는 테이블이 없을 때만 `schema.sql` 을 적용. 이후 DDL 변경은 수동 `psql` 또는 마이그레이션 도구(Flyway 등) 도입 필요 |
| DB 데이터 | VM 의 PostgreSQL 에 영속. 기존 백업 체계에 `fileupload` DB 포함시킬 것 |
| 업로드 파일 | S3 모드면 재배포와 무관하게 유지. local 모드는 컨테이너 내부라 재생성 시 사라짐 |
| 로그 | `docker logs file-upload-block` (json-file, 10MB × 5 회전). 차단은 INFO/WARN, `[SUSPICIOUS]` 접두어가 의심 신호 |
| 비밀값 변경 | Secrets 수정 → `Run workflow`(태그 미지정) 로 `.env` 재생성 + 재배포 |
| 시연 초기화 | `psql -U fileupload -d fileupload` 에서 `TRUNCATE file_upload, ip_block, policy_change_log; ` 후 정책 토글 초기화. 완전 초기화는 DB 를 지우고 2-3 부터 다시 |
| Cloudflare 대역 갱신 | `sudo refresh-cloudflare-ips.sh` (분기 1회). 갱신이 밀리면 새 엣지 IP 에서 온 요청의 실제 IP 를 못 읽어 그 엣지 IP 로 제한이 걸림 |
| Cloudflare 제한 | 본문 100MB(Free), 오리진 응답 대기 100초. 앱 상한과 같아 평소엔 영향 없음 |
| 독립 구성 | DB 까지 컨테이너로 띄우는 단일 호스트 데모는 `docker compose -f docker-compose.prod.yml up -d --build` (`.env.example` 참고) |
