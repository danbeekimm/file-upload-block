# 배포 가이드 (EC2 단일 호스트)

Docker 멀티스테이지 빌드(Gradle 래퍼)로 어디서든 동일하게 빌드·실행됩니다.
로컬에서 `docker-compose.prod.yml`로 검증한 구성을 그대로 EC2에 올립니다.

## 0. 준비물

- EC2 인스턴스 (Ubuntu 22.04+, t3.small 이상 권장 — 빌드 시 메모리 필요)
- 보안 그룹: 인바운드 22(SSH, 내 IP만), 80 또는 8080(HTTP, 전체)
- S3 접근 권한 (아래 1번)

## 1. S3 자격 증명과 권한

S3 자격 증명은 `.env`의 `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`로 전달합니다 (`.env.example`의 항목 그대로).
compose가 이 값을 컨테이너 환경 변수로 주입하고 애플리케이션이 그대로 사용합니다.
둘 다 비워 두면 SDK 기본 자격 증명 체인을 쓰므로, EC2에 IAM 역할을 연결한 경우에는 키 없이도 동작합니다.

키(IAM 사용자) 또는 역할에 연결할 정책:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::work-841820566166-us-east-1-an/uploads/*"
    }
  ]
}
```


## 2. 서버 셋업

```bash
# Docker 설치 (Ubuntu)
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER && newgrp docker

# 소스 배치 (git 또는 scp)
git clone <repo-url> file-upload-block && cd file-upload-block

# 환경 변수
cp .env.example .env
vi .env        # DB_PASSWORD 필수. AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY 채우기 (IAM 역할 사용 시에는 비워 둠)
```

## 3. 실행

```bash
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml logs -f app   # 기동 확인
```

- DB는 컨테이너 네트워크 내부에만 존재 (호스트 포트 미노출)
- 앱은 `${APP_PORT:-8080}`으로 노출 → `http://<EC2 퍼블릭 IP>:8080`
- 최초 기동 시 `schema.sql` 자동 적용 (고정 확장자 7개 시드 포함)

배포 확인 체크리스트:

```bash
curl http://localhost:8080/api/admin/policies                     # 200 + 고정 7개
curl -X POST http://localhost:8080/api/uploads -F files=@some.txt # STORED
# 화면에서 exe 체크 후:
curl -X POST http://localhost:8080/api/uploads -F files=@evil.exe # BLOCKED_EXTENSION
```

## 4. (선택) 80 포트 / HTTPS

시연용으로는 8080 직접 노출로 충분합니다. 80/HTTPS가 필요하면 Caddy를 앞에 둡니다:

```bash
docker run -d --name caddy --network host caddy:2-alpine \
  caddy reverse-proxy --from :80 --to localhost:8080
```

> 프록시를 두는 순간 클라이언트 IP가 프록시 IP로 바뀝니다. IP 기반 기능(요청 제한, IP 차단)을
> 살리려면 X-Forwarded-For 신뢰 설정이 필요한데, 이는 의도적으로 범위에서 제외했습니다
> (CONSIDERATIONS.md — 배포 토폴로지 확정 전에 넣으면 헤더 위조로 우회됨).

## 5. 운영 메모

| 항목 | 내용 |
|---|---|
| 갱신 배포 | `git pull && docker compose -f docker-compose.prod.yml up -d --build` |
| DB 데이터 | `prod-db-data` 볼륨에 영속. 컨테이너 재생성에도 유지 |
| 업로드 파일 | S3 모드면 서버 재배포와 무관하게 유지. local 모드는 컨테이너 내부라 휘발 — 시연은 s3 권장 |
| 로그 | `docker compose logs`. 차단은 INFO/WARN, `[SUSPICIOUS]` 접두어가 의심 신호 |
| 시연 초기화 | `docker compose -f docker-compose.prod.yml down -v` 후 재기동 (정책·기록 초기화) |
