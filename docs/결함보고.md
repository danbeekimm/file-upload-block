## 1. 클라이언트 오류가 전부 500으로 응답됨

**증상** — 다음 요청이 모두 `HTTP 500` + `{"code":"INTERNAL_ERROR","message":"서버 오류가 발생했습니다. …"}`로 응답되고, 매번 `GlobalExceptionHandler : unexpected error` ERROR 로그가 남는다.

| 요청 | 기대 |
|---|---|
| `PUT /api/admin/policies/fixed/exe` 본문 `{}` (`@NotNull` 위반) | 400 |
| `PUT /api/admin/policies/fixed/exe` 본문 `{bad` (깨진 JSON) | 400 |
| `GET /api/uploads/not-a-uuid` (타입 불일치) | 400 또는 404 |
| `POST /api/uploads` 멀티파트 아님 | 400 |
| `POST /api/uploads -F other=@x` (`files` 파트 없음) | 400 |
| `POST /api/admin/policies/custom` extension 101자 (`@Size(max=100)` 위반) | 400 |
| `GET /no-such-path` | 404 |

```bash
curl -s -w '\nHTTP %{http_code}\n' -X PUT localhost:8099/api/admin/policies/fixed/exe \
  -H 'Content-Type: application/json' -d '{}'
# {"code":"INTERNAL_ERROR","message":"서버 오류가 발생했습니다. 잠시 후 다시 시도해 주세요."}
# HTTP 500
```

**원인** — `src/main/java/com/study/fileupload/common/GlobalExceptionHandler.java:29`의
`@ExceptionHandler(Exception.class)`가 모든 예외를 받는다. Spring MVC는 `@ControllerAdvice`의 핸들러를
기본 처리(`DefaultHandlerExceptionResolver`: 400/404/405/415 변환)보다 먼저 적용하므로
`MethodArgumentNotValidException`, `HttpMessageNotReadableException`, `MethodArgumentTypeMismatchException`,
`MultipartException`, `MissingServletRequestPartException`, `NoResourceFoundException`이 전부 이 핸들러로 들어간다.

부수 효과로 `UploadService.process`의 400 `NO_FILES` 분기는 도달하지 않는다. `@RequestParam("files")`가
필수 파라미터라 컨트롤러에 들어오기 전에 예외가 나기 때문이다.

**영향** — 클라이언트 실수가 서버 장애로 기록된다. 로그만 보면 구분이 안 되고, 화면은 "서버 오류" 메시지를 보여 준다.

**수정** — `GlobalExceptionHandler`에 클라이언트 오류 핸들러를 추가. 본문 검증 실패 → 400 `INVALID_REQUEST`(필드별 detail),
깨진 JSON·타입 불일치·파라미터 누락 → 400 `INVALID_REQUEST`, `files` 누락·멀티파트 아님 → 400 `NO_FILES`, 없는 경로 → 404 `NOT_FOUND`,
허용되지 않은 메서드 → 405, Content-Type → 415. 클라이언트 오류는 INFO로만 기록하고 `Exception` 핸들러는 폴백으로 남김.

**검증** — `ErrorResponseIntegrationTest` 4개. 위 7개 요청을 실제 앱에 다시 보내 전부 400/404/405 확인, ERROR 로그 0건.

## 2. 확장자 20자 초과 파일 → 요청 전체 500

**증상** — 내용이 평범한 텍스트여도 이름이 `a.abcdefghijklmnopqrstuvwxyz`(확장자 26자)이면 요청 전체가 500이다.

```bash
printf hello > a.abcdefghijklmnopqrstuvwxyz
curl -s -w '\nHTTP %{http_code}\n' -X POST localhost:8099/api/uploads -F files=@a.abcdefghijklmnopqrstuvwxyz
# {"code":"INTERNAL_ERROR", …}   HTTP 500
# 로그: ERROR: value too long for type character varying(20)
```

**원인** — `file_upload.extension`은 `VARCHAR(20)`(`schema.sql`)인데, 기록 생성 시 확장자 길이를 검증하거나 자르지 않는다.

- `src/main/java/com/study/fileupload/upload/FileUploadRecord.java:64` — `@Column(length = 20) private String extension;`
- `src/main/java/com/study/fileupload/upload/UploadService.java:256` (`stored`), `:281` (`rejected`) — `info.extension()`을 그대로 넣음
- `FilenameProcessor.validate`는 전체 이름 255바이트만 본다. 확장자 길이 제한은 커스텀 정책 입력(`ExtensionNormalizer`)에만 있다

저장 경로에서는 객체를 저장소에 올린 뒤 DB 저장이 실패하고(객체는 롤백 삭제됨), 예외가 `judgeAndRecord`의 catch(`RejectException`, `IOException`만 잡음)를 지나쳐 요청 전체를 500으로 만든다.
거부 경로(`recordRejection`)에서 터져도 마찬가지다.

**같은 원인의 변형 (코드로만 확인)** — 255바이트 이름의 점 파일은 다운로드 이름에 `_`가 붙어 256자가 되어 `download_name VARCHAR(255)`를 넘는다.

**영향** — 사용자가 이름만으로 500을 만들 수 있다. 다중 파일 요청이면 앞서 저장된 파일의 기록은 남지만 응답은 오지 않아 결과를 알 수 없다.

**수정** — `FilenameProcessor.validate`: 확장자 20자 초과 → `INVALID_FILENAME`("확장자가 너무 깁니다. (최대 20자)"), 점으로 시작하는 이름은 `_` 접두어를 감안해 254바이트까지만 허용.
`FileUploadRecord`: 거부 기록의 `original_name`은 255자로 자르고 20자를 넘는 확장자는 NULL로 기록해, 기록 저장 자체는 실패하지 않게 함.

**검증** — `FilenameProcessorTest.validate_lengthLimitsMatchDb`, `UploadFlowIntegrationTest.overlongNamesAreRejectedPerFile`
(확장자 21자·300자 이름 → 파일별 `INVALID_FILENAME`, 거부 기록 2건 저장, 같은 요청의 정상 파일 STORED). 실제 앱: 26자 확장자 파일 + png → 200, 파일별 결과.

## 3. `.jpeg` 업로드에 "PNG로 변환" 안내 + 다운로드 이름 `.jpg`로 변경

**증상**

```bash
curl -s -X POST localhost:8099/api/uploads -F files=@photo.jpeg
# {"results":[{"fileName":"photo.jpeg","status":"STORED",…,"notices":["PNG로 변환되어 저장되었습니다."]}]}
```

DB 확인: `original_name=photo.jpeg`, `download_name=photo.jpg`, `content_type=image/jpeg`. 실제로는 JPEG으로 재인코딩되었고 PNG가 아니다.

**원인** — `src/main/java/com/study/fileupload/upload/UploadService.java:189-194`

```java
String newExt = trusted.storeAs().extension();            // StoreAs.JPEG → "jpg"
if (newExt != null && !newExt.equals(info.extension())) { // "jpg" != "jpeg" → 진입
    downloadName = replaceExtension(downloadName, newExt);
    notices.add("PNG로 변환되어 저장되었습니다.");         // webp 전용 문구가 고정
}
```

이 분기는 webp → PNG 재저장(명세 5-3)을 위한 것인데, `jpeg` 확장자도 `StoreAs.JPEG`의 대표 확장자 `jpg`와 달라 같은 분기를 탄다.

**영향** — 틀린 안내 문구. 다운로드 이름이 사용자가 올린 이름과 달라진다 (`photo.jpeg` → `photo.jpg`).

**수정** — `UploadService.storeAndRecord`: 저장 MIME이 원래 MIME과 다를 때(webp → PNG)만 확장자를 바꾸고, 안내 문구는 바뀐 형식 이름으로 생성.

**검증** — `UploadFlowIntegrationTest.jpegKeepsNameWithoutConversionNotice`(notices 없음, 다운로드 `image/jpeg` + `photo.jpeg`). 실제 앱 + DB: `download_name = photo.jpeg`.

## 4. 25MB 초과 단일 파일 → "전체 크기 100MB" 메시지로 요청 전체 거부

**증상**

```bash
dd if=/dev/zero of=big.bin bs=1m count=26
curl -s -w '\nHTTP %{http_code}\n' -X POST localhost:8099/api/uploads -F files=@big.bin
# {"code":"REQUEST_TOO_LARGE","message":"한 번에 올릴 수 있는 전체 크기는 100MB입니다."}
# HTTP 413
```

요청 전체는 26MB로 100MB 상한 안인데, 메시지는 전체 크기 초과라고 말한다. 명세 6장이 의도한 결과는 파일별
`SIZE_EXCEEDED`("파일은 25MB를 넘을 수 없습니다") 부분 성공 응답이다.

**원인** — 두 상한이 같은 값이다.

- `src/main/resources/application.yml:14` — `spring.servlet.multipart.max-file-size: 25MB`
- `schema.sql` — `upload_policy.max_file_bytes DEFAULT 26214400` (25MB)

파일이 25MB를 넘으면 멀티파트 파싱 단계에서 `MaxUploadSizeExceededException`이 먼저 나고,
`GlobalExceptionHandler.java:24`의 `handleTooLarge`는 이를 항상 요청 전체 초과로 간주해 고정 문구를 돌려준다.
따라서 이미지 외 파일의 파일별 `SIZE_EXCEEDED` 경로는 실제 요청으로는 도달하지 않는다 (이미지는 10MB 상한이라 도달함).

**영향** — 틀린 메시지. 다중 파일 요청에서 큰 파일 하나 때문에 나머지 파일까지 전부 거부된다.

**수정** — `application.yml`의 `max-file-size`를 요청 상한과 같은 100MB로 올려, 파일별 상한은 항상 파이프라인이 판정하게 함.
`handleTooLarge`의 메시지는 설정값(`MultipartProperties.maxRequestSize`)에서 만들어 하드코딩 제거. 명세 6장의 "크거나 같아야"를 "커야"로 정정.

**검증** — `UploadFlowIntegrationTest.oversizedFileIsRejectedPerFile`. 실제 앱: 26MB + png → 200, `big.bin`만 `SIZE_EXCEEDED`("파일은 25MB를 넘을 수 없습니다 (현재 26.0MB)"), png STORED.

## 보고에서 제외한 것

다음은 동작 오류가 아니라 구조·취향의 영역이라 결함으로 올리지 않았다: `upload`·`guard` 패키지 상호 참조,
요청 수 제한이 `file_upload` 기록에서만 파생되는 점, 가드 필터가 `ActorResolver`를 거치지 않는 점,
파일 스트림을 단계마다 다시 여는 점, `TrustedFileType.inlineAllowed`가 판정에 쓰이지 않는 점.
